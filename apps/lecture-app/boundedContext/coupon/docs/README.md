## 현재 범위

쿠폰 한 장은 주문 항목의 강의 하나에 한 번 사용한다. 정액·정률, 단독·중첩, 선착순 발급을 지원한다. 최소 결제액은 없으며 0 HP 결제를 허용한다. 판매자 할인 후 플랫폼 할인을 계산한다.

판매자 쿠폰은 판매자가 신청하고 관리자가 승인하며, 판매 대금 감소로 판매자가 부담한다. 플랫폼 쿠폰은 **관리자만 발행**하고, 플랫폼이 프로모션 지갑에 재원을 충전하여 할인액을 부담한다.

특정 강의를 대상으로 한 플랫폼 쿠폰이 열려 있거나 미사용 발급 쿠폰이 남아 있는 동안 그 강의 가격을 올릴 수 없다. 판매자 쿠폰은 제한하지 않는다.

주문 전체 쿠폰·비례 배분·다른 강의 할인 재계산·할인 회수·추가 결제·공동 부담은 현재 구현에서 제외한다. 예산은 특정 강의 쿠폰이면 가격 × 할인율 × 수량(가격 인상 제한이 지킨다), 모든 강의 대상 정률 쿠폰이면 관리자가 입력한 장당 최대 할인액 × 수량이다.

구조는 `:lecture-app`을 유지하고 그 안에 Gradle 하위 프로젝트 `:coupon`을 두는 것이다. 배포는 지금처럼 lecture-app pod 하나에 강의와 쿠폰이 함께 실린다. 다만 **JVM이 나뉘어 있다고 가정**해 강의 ↔ 쿠폰은 내부 HTTP API와 Kafka로만 통신하고 트랜잭션은 연결하지 않는다. Spring Modulith는 모듈 경계 검증과 이벤트 externalization에 쓴다. 자세한 것은 [구조와 처리 흐름](design.md#모듈-경계).

## 구현 준비 상태

발급·사용 구조는 구현할 수 있다. 계산 세부 정책, billing DTO, 운영 수치는 [남은 결정](decisions.md#구현-전-남은-결정)을 확정해야 한다. 미확정 정책을 구현자가 임의로 확정한 것으로 취급하지 않는다.

FE 범위(1차): 발급 버튼의 "처리 중" 표시와 요청 상태 폴링, 보유 쿠폰함, 주문 화면의 추천 조합 표시와 변경, 판매자 쿠폰 신청 화면, 관리자 승인·발행·중단 화면.
