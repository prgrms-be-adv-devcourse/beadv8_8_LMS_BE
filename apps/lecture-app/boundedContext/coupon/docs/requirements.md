# 기능·비기능 요구사항

## 기능

| ID | 요구사항 |
| --- | --- |
| F1 | 판매자가 판매자 쿠폰을 신청하고 관리자가 승인·거절한다. 플랫폼 쿠폰은 관리자만 발행한다 |
| F2 | 모든 쿠폰을 수량 제한 선착순으로 발급한다. 회원당 정책별 한 장이며 복원은 재발급이 아니다 |
| F3 | 접수는 처리 중으로 표시하고 요청 ID로 확정 결과를 조회한다 |
| F4 | 정액·정률, 특정 강의·플랫폼의 모든 강의 중 하나 대상, 상대·고정 기간을 지원한다 |
| F5 | 최대 할인 조합과 강의별 배치를 추천하고 회원이 쿠폰과 적용 강의를 바꿀 수 있다 |
| F6 | 단독·중첩 제약과 판매자 → 플랫폼 순서를 검증한다. 선택한 쿠폰을 일괄 예약한다 |
| F7 | 0 HP를 포함해 주문·취소·지급을 완료한다. 양수인 플랫폼 재원 처리는 생략하지 않는다 |
| F8 | 취소한 항목의 구매자 결제액을 반환하고 플랫폼 부담은 해당 예약으로 복구한다 |
| F9 | 유효기간이 남은 쿠폰만 복원한다. 다른 강의 금액은 재계산하지 않는다 |
| F10 | 보유 쿠폰·사용 이력·발급 결과·예산 작업 결과를 조회하고 운영자가 장애를 복구할 수 있다 |
| F11 | 특정 강의 대상 플랫폼 쿠폰이 열려 있거나 미사용 발급 쿠폰이 남은 동안 그 강의의 가격 인상을 거부한다. 판매자 쿠폰과 가격 인하는 제한하지 않는다 |
| F12 | 마지막 1장 발급 뒤 매진 신호를 남기고, 매진 뒤 몰리는 요청은 짧은 메모리 캐시로 Redis 호출 없이 거절한다. 최종 판정은 Lua다 |

## 비기능

| ID | 요구사항 |
| --- | --- |
| N1 | DB 확정 발급 수 ≤ 총수량, 회원별 중복 발급 금지, 발급 쿠폰의 동시 사용 금지 |
| N2 | 접수에 Redis Lua·Stream, 전달에 Kafka·DLT를 사용한다. 신규 발급 DB OUTBOX는 추가하지 않는다 |
| N3 | 재전송·응답 유실·이벤트 역전에도 업무 효과는 한 번만 반영한다. 같은 ID의 다른 내용은 충돌이다 |
| N4 | 사용 이력과 현재 상태는 같은 쿠폰 트랜잭션으로 갱신한다. 모듈 간 트랜잭션은 분리한다 |
| N5 | 분산락은 SWR 조회 갱신에만 사용한다. 사용 정합성은 DB CAS·제약으로 보장한다 |
| N6 | Redis 장애 시 발급은 차단하고 기존 쿠폰 사용·취소는 DB·billing으로 계속한다 |
| N7 | 공유 Redis·lecture pod의 용량을 측정하고 상한·적체 차단을 최초 운영 전에 적용한다 |
| N8 | 발급 요청과 사용·예산 작업을 식별자로 추적한다. 결과 불명을 성공·실패로 임의 확정하지 않는다 |
| N9 | 강의 ↔ 쿠폰은 내부 HTTP API와 Kafka로만 통신한다(JVM 분리 가정). Java 직접 호출·인프로세스 이벤트·스키마 간 JOIN·FK·Repository 접근을 금지한다 |
| N10 | 사용자 API는 로그인 회원 기준으로 소유권을 검사하고 관리자 작업은 관리자 권한으로 제한한다 |

## 제외 범위

출연·충전 쿠폰, 공동 부담, 주문 전체 할인, 비례 배분, 부분 취소 시 다른 강의 재계산·할인 회수·추가 결제, 자동 지급·회원별 N장 발급은 제외한다. 대기실·고급 운영 화면은 후속이다. DLT 격리·조회·안전한 재처리 자체는 1차에 필요하다.
