# 작업 흐름 (오케스트레이션)

오케스트레이터 세션이 이슈와 작업 지시서를 만들고, BE·FE 세션이 구현하며, 오케스트레이터가 리뷰·검증한다.

## 역할

| 역할 | 하는 일 |
| --- | --- |
| 오케스트레이터 (kdt 세션) | 이슈·작업 지시서 작성, 세션 투입, 진행 추적, 리뷰 결과 검증, 보고. FE PR은 BE 계약과 비교해 직접 병합 |
| BE 세션 | 쿠폰 모듈 구현(worktree), 테스트, Codex 리뷰 반영, 보고서, 승인 뒤 PR |
| FE 세션 | 쿠폰 화면 구현(worktree), BE 계약 기준 검증, 보고서, 승인 뒤 PR |
| 사용자 | 결정, 보고서 리뷰, **BE PR 점검·병합**, billing 계약·코드 변경 |

## BE 흐름

1. 오케스트레이터가 [`decisions.md`](decisions.md) "구현 순서"의 한 단계를 BE 이슈로 만든다(사용자 명령 뒤). 작업 지시서에 수정 범위, 수정 금지 범위, 지켜야 할 invariant, 완료 조건, 돌릴 테스트를 적는다.
2. BE 세션이 worktree에서 구현하고 자체 테스트를 통과시킨다. 브랜치 `feature/tkt-<번호>`에 로컬 커밋한다(push 없음).
3. 테스트 세션 검증 → **Codex 리뷰(최대 5회)** → 검증한 지적만 반영. 5회 안에 해결되지 않으면 멈추고 남은 지적을 보고한다. 리뷰 반영으로 코드가 바뀌면 테스트를 다시 받는다.
4. 보고서를 `reports/`에 쓴다(바꾼 파일, 돌린 테스트와 결과, 건드린 invariant, 지시서와 다르게 한 부분과 이유, 미결).
5. 오케스트레이터가 보고서와 diff를 작업 지시서·설계 문서와 비교해 검증하고 사용자에게 보고한다.
6. 사용자가 IDE에서 브랜치를 dev와 비교해 점검하고 승인 → 세션이 push·PR. **PR 점검과 병합은 사용자가 한다.**

## FE 흐름

1. 해당 BE 단계의 PR이 열린 뒤, 오케스트레이터가 [`contracts.md`](contracts.md)와 BE PR의 실제 API(경로·DTO·상태·오류 코드)를 기준으로 FE 이슈와 작업 지시서를 만든다.
2. FE 세션이 worktree에서 구현한다. Codex 리뷰는 BE와 같이 최대 5회다.
3. 오케스트레이터가 FE 결과를 **BE 계약과 비교**해 검증한다: 경로·필드 이름·상태 값·오류 처리·"처리 중" 표시·폴링.
4. 보고서 → 사용자 보고 → 승인 → PR. **FE PR은 오케스트레이터가 CI 통과를 확인하고 바로 병합한다**(squash). 병합 순서는 보고한 순서대로이며 막히면 멈추고 보고한다.

## 공통 규칙

- 로컬 커밋은 승인 전에도 할 수 있다(사용자가 IDE에서 브랜치를 dev와 비교해 점검한다). push·PR·이슈 닫기는 승인 뒤에만. 이슈 생성은 사용자가 작업 시작을 명령한 뒤에만.
- BE와 FE는 같은 단계라도 BE가 먼저다. FE는 열린 BE PR의 계약을 기준으로 한다.
- billing 계약·코드는 사용자가 직접 바꾼다. 세션은 요청 문서만 쓴다.
- 결정이 바뀌면 `decisions.md`와 해당 문서를 같은 변경에서 고친다. 오케스트레이터가 `/Users/yong/Workspaces/kdt/coupon/`의 원본과 `boundedContext/coupon/docs/`를 같은 내용으로 유지한다.
- 진행 현황은 `/Users/yong/Workspaces/kdt/coupon/STATUS.md`에 둔다(이슈·세션·PR·병합 기록).

## 구현 순서

[`decisions.md`](decisions.md) "구현 순서와 담당 경계" 1~7을 따른다. 1단계(정책·API 계약)와 2단계(구조 준비)는 BE 한 이슈로 묶을 수 있다. FE는 3단계(발행·승인·발급·요청 조회)부터 붙는다.
