# 고도화 작업 절차

테스트 기준은 [테스트 기준](test-criteria.md)에 있다.

## 고도화 단계

사용자 결정(2026-10-29)에 따라 아래 1~4번을 모두 구현한다. 진행 순서는 **회원 이벤트 Kafka 전환 → Redis Pub/Sub 전환 → 단체방 구현**이다. 3번 서비스 인터페이스 분리는 1·2번 전환 중 함께 수행하고, 4번 착수 전에 적용 결과를 확인한다. 이름·배치는 [서비스 경계 규칙](../rules/decisions.md#서비스-경계-규칙-사용자-결정-2026-10-29)을 따른다. 이 문서의 단계가 설계 문서의 기존 병렬 진행 제안보다 우선한다.

| 단계 | 구현 범위 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1. 회원 이벤트 Kafka 전환 | shared 회원 이벤트 발행·소비, chat 회원 복제·버전 기반 백필·제어 outbox. 해당 회원 서비스 인터페이스를 `app`에 두고 Facade 의존을 교체한다. Kafka 수신은 `in`, 외부 발행 구현은 `out`, 업무 처리 구현은 `app`에 둔다 | 실제 Kafka Testcontainers로 가입·변경·중복·역순·백필과 업무 변경·제어 outbox의 원자성을 검증한다. 테스트 세션·리뷰·보고 절차를 마친 뒤 2단계로 진행한다 |
| 2. Redis Pub/Sub 전환 | 메시지·시스템 안내·연결 제어 outbox relay, Pub/Sub 발행·구독, 로컬 STOMP 전달·이력 복구. 해당 서비스와 전파 계약을 `app` 인터페이스로 분리하고 Redis 구현을 `out/redis`에 둔다. Streams는 구현하지 않는다 | 실제 Redis Testcontainers로 발행·수신·장애·재시도·중복·lease 회수를 검증한다. 회원 상태 변경 후 단일 chat-app의 대상 로컬 연결 전체 종료, 일반·시스템 메시지 전달·마지막 유실 복구를 FE·k3d E2E로 통합 검증한다 |
| 3. 서비스 인터페이스 분리(1·2번과 함께 적용) | 전환 대상 Facade가 `app`의 역할 중심 인터페이스를 사용한다. 업무 구현은 `app`, Redis 등 외부 시스템 구현은 `out`, 수신 어댑터는 `in`에 배치한다 | Facade의 구현체 직접 의존과 기술 중심 인터페이스 이름이 없는지 확인하고 권한·트랜잭션·실패 복구 회귀 검증을 통과한다 |
| 4. 단체방 구현 | `GROUP` 도메인·Flyway·생성·초대·퇴장·재입장·강퇴·폐쇄 API, 방장 권한, FE, 관리자 기록을 구현한다. 해당 기능의 미정 정책·FE 계약을 먼저 확정하고 서비스 인터페이스 규칙을 적용한다 | replica 1개의 단체방 E2E, 참여 세대·가시 범위·읽음·재전송, 동시 참여·최대 인원, 행위자·대상 기록, 기존 1:1 회귀 검증을 통과한다. 기존 1000명 안의 부하 시험 결과와 한계를 기록한다 |

1단계는 제어 작업 저장까지 검증하며, Redis 도입 전 대상 로컬 연결 전체의 즉시 종료를 완료했다고 보고하지 않는다. 2단계에서 연결 제어를 통합 검증한다. 각 단계는 자체 검증 결과를 남기며, 운영 전환은 설계 문서의 인증·서비스 경계 검증까지 통과한 뒤 진행한다.

**4번 단체방 구현까지 이번 고도화의 필수 범위다.** 단체채팅의 미정 정책·FE 계약은 전환 작업과 독립적으로 정리할 수 있다. 1~3번 완료만으로 전체 고도화를 완료했다고 보고하지 않는다.

각 단계에서 [설계 문서](../final-design.md) 4.6·4.7의 급증 대응을 적용한다. Redis 전환에서는 제한된 executor·relay·송신 버퍼·장애 적체 제어를, 서비스 분리에서는 실제 저장 트랜잭션 축소를, 단체방에서는 불변 수신자 집합·참여 집계와 입력 제한을 구현한다. 4번 완료 및 출시 판단 전에 인기 방·지속 과부하·재접속·장애 혼합 시험과 Q12의 수용 기준을 확정한다. 사용자가 적다는 이유로 검증을 미루지 않는다.

## 각 단계의 작업 절차

Kafka 회원 이벤트 처리, WebSocket 메시지의 Redis Pub/Sub 처리, 단체채팅 구현에 아래 절차를 각각 적용한다. 사용자가 구현 시작을 명령한 뒤에 이슈 생성부터 시작한다. 이 문서 갱신 요청만으로 구현·이슈 생성·다른 세션 전달을 시작하지 않는다.

1. **이슈 생성**: 회원 이벤트 Kafka 전환·Redis Pub/Sub 전달·단체채팅을 각각 이슈로 관리한다. 기존 해당 이슈가 있으면 재사용한다. 이슈 형식·라벨은 [`docs/contributing/git-workflow.md`](../../../../docs/contributing/git-workflow.md)를 따르고, 프론트 변경이 필요하면 FE 이슈를 따로 만든다. 본문에 설계 문서의 해당 장과 완료 증거를 적는다. 단체채팅은 이번 고도화의 필수 완료 조건에 포함한다.
2. **전달과 병렬 실행**: 오케스트레이터가 백엔드 세션과 프론트엔드 세션에 이슈를 전달한다. 각 세션은 현재 고도화 단계 안에서 서로 의존하지 않는 하위 작업을 서브에이전트로 나눠 병렬 실행한다. Kafka 전환과 Pub/Sub 전환 자체를 동시에 구현하지 않는다.
   - 서브에이전트마다 담당 파일 범위를 나눠 같은 파일을 동시에 고치지 않는다. 겹치면 worktree를 분리한다.
   - 백엔드와 프론트가 함께 바꾸는 계약(STOMP 경로, payload, 재동기화 신호, 단체채팅 생성·참여·재입장·권한·관리자 기록 API)은 착수 전에 문서로 맞춘다.
3. **테스트 세션 검증**: 구현을 마친 세션은 커밋하지 않은 채 테스트 세션(`test-agent`, 이름이 바뀌었으면 `ListAgents`로 확인)에 SendMessage로 테스트를 요청한다. 요청에는 이슈 번호, 브랜치·worktree 경로, 변경 파일, [테스트 기준](test-criteria.md) 중 해당 항목을 적는다.
   - 테스트 세션은 백엔드·프론트 테스트를 맡는다. [테스트 기준](test-criteria.md)에 빠진 테스트를 보강하고, 백엔드는 `./gradlew check`, 프론트는 프론트 `AGENTS.md`의 순서(format, lint, test, build)를 통과시킨다. Kafka·Redis 통합 테스트는 [`docs/dev/testing.md`](../../../../docs/dev/testing.md)의 Testcontainers 설정을 `@Import`한다.
   - 테스트 세션은 결과(실행 명령, 테스트 수·실패 수, 추가한 테스트, 실패 원인)를 요청한 세션에 돌려준다. 실패가 구현 문제면 구현 세션이 고치고 다시 요청한다. 테스트 세션 통과 없이 다음 단계로 넘어가지 않는다.
4. **Codex 리뷰**: 테스트 세션 통과 뒤, 커밋 전 미커밋 변경(구현과 테스트 세션이 추가한 테스트 모두)을 Codex `sol-6.1`, 추론 강도 `xhigh`로 리뷰한다. 리뷰 반영으로 코드가 바뀌면 3단계 테스트를 다시 받는다.
   ```bash
   codex review -c model="sol-6.1" -c model_reasoning_effort="xhigh" "<리뷰 지침>"
   ```
   지적은 실제 코드와 대조해 맞음·근거 부족·틀림으로 판단하고, 맞는 지적만 반영한다. 정책·제품 판단이 필요한 지적은 질문으로 남긴다.
5. **보고와 사용자 리뷰**: 원격에 올리기 전에 보고서를 만들어 사용자 리뷰를 받는다. 보고서에는 이슈별 변경 요약, 테스트 세션 검증 결과(테스트 수·실패 수, 추가한 테스트), Codex 지적 판단표, 남은 질문, 커밋 메시지·PR 본문 초안을 넣는다.
6. **원격 반영**: 사용자가 승인한 뒤에만 커밋·push·PR 생성을 한다. 승인 전에 push, PR, 이슈 닫기를 하지 않는다.
