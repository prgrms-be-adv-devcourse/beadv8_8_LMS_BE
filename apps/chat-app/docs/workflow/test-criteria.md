# 테스트 기준

테스트 세션이 검증하고 보강할 기준이다. 실행 절차는 [작업 절차](process.md) 3단계에 있다.

- 회원 이벤트: 같은 이벤트 2회, 옛 `version`, 변경 이벤트가 가입보다 먼저 오는 경우, 정지·강등 시 단일 chat-app의 대상 로컬 연결 전체 종료를 검증한다.
- 단계별 검증: Kafka 단계에서는 회원 반영·제어 outbox 원자 저장까지 확인하고, 대상 로컬 연결 전체 종료는 Redis 단계의 통합 검증에서 완료한다. 상세 순서는 [작업 절차의 고도화 단계](process.md#고도화-단계)를 따른다.
- 서비스 경계: 전환한 Facade가 `app` 인터페이스를 주입받고 Redis·Kafka 구현체에 직접 의존하지 않는지 리뷰한다. 업무 서비스 검증과 실제 Kafka·Redis 어댑터 통합 검증을 함께 수행하며, 인터페이스 추출 전후의 권한·트랜잭션·재전송·실패 복구 동작이 유지되는지 확인한다.
- Outbox 적재: 메시지·outbox·초기 발행 체크포인트의 원자성, 선점 직후 종료·lease 회수, XADD 뒤 DB 결과 기록 전 종료, 늦은 `claimToken` 결과 무시, consumer 선처리 상태 보존을 검증한다.
- Stream 소비: 같은 그룹 worker의 분담, 재시작 시 그룹 위치 보존, XREADGROUP 후 종료·XAUTOCLAIM cursor 순회, pending의 backoff·횟수 제한·격리 후 ACK를 검증한다. 별도 그룹의 독립 소비·ACK는 최소 Redis 계약 테스트로 확인하며 알림 앱 구현을 요구하지 않는다.
- Pub/Sub·체크포인트: PUBLISH 뒤 DB 기록 전 종료의 중복, DB 기록 뒤 XACK 전 종료의 재발행 생략, 사용자 수신과 ACK의 분리, 로컬 세션 없는 회원·구독자 0명, 참여 세대·FE 중복 제거·순번 복구를 검증한다.
- Stream 유실·보존: ENQUEUED 뒤 Redis Stream/그룹 데이터 유실을 DB 미완료 대조로 재구성한다. 중복 재적재 제한, DEAD의 자동 재진입 방지, 운영 재처리 세대, 격리 저장 실패 시 ACK 금지, XACK 후 본문 보존과 미소비·pending 보호 정리 경계를 검증한다. 영속화·noeviction·OOM 대응·메모리 상한은 운영과 맞춘 명시적 Redis 설정으로 별도 시험하고 일반 smoke test로 대체하지 않는다.
- 누적 수신 커서: 참여 행의 `last_received_sequence` 추가·기존 데이터 NULL·재입장 초기화, 인증 사용자/활성 참여/세대/가시 범위/상한 검증, 같은 값·낮은 값·동시 ACK의 단조 증가, 퇴장·재입장 경합, DB 실패·응답 유실 재시도와 읽음의 독립성을 검증한다. 서버 발행 성공만으로 수신 값을 올리지 않는다.
- 기기별 복구: 중간 누락 뒤 높은 순번 도착·숨겨진 순번·여러 페이지 대조·마지막 유실, 한 기기 ACK 뒤 다른 기기의 누락, 로컬 데이터 유실 시 서버 회원 커서를 복사하지 않는 재동기화를 검증한다. 서버 기기별 테이블 없이 각 기기의 확인 위치를 사용한다.
- 수신 부하: 참여가 고정된 500명 방에서 메시지당 수신 행 500개를 INSERT하지 않음을 확인한다. 개별/누적 ACK의 UPDATE·WAL·경합·표시 지연을 비교하고 지속 유입 중 ACK 최대 대기·대기 방 수·재시도 상한을 검증한다. 수신 UPDATE의 방 순번 잠금 미획득과 ACK별 방 전체 재방송 방지를 확인하고 1000명 부하 시험에도 포함한다.
- 단체채팅: 생성·초대·퇴장·재입장·강퇴·폐쇄의 확정 정책, 동시 참여 시 최대 인원, 방장 권한·퇴장·자격 상실, 행위자·대상 기록, 참여 세대·가시 범위·읽음·재전송 불변식을 검증한다. 1000명 안의 방 잠금 경합·DB 조회·전달 지연·메모리를 부하 시험하고 결과와 한계를 기록한다. 기존 1:1 동작도 회귀 검증한다.
- 방 topic(2026-10-30 사용자 결정): 퇴장·강퇴·폐쇄·재입장이 커밋된 뒤 저장된 메시지는 구독이 남아 있어도 그 회원(이전 세대)의 세션에 가지 않는다. 즉시 회수 신호를 일부러 버려도 수신자 집합 버전 확인이 막는지, 강퇴 직후·재입장 직후·SUBSCRIBE 처리 중 퇴장의 경합을 시험한다. 늦은 등록 경합을 결정적으로 재현한다: 방 버전 10에서 느린 SUBSCRIBE가 버전 8의 상태(참여 중)를 읽고 멈춘 사이 버전 9 퇴장 커밋과 다른 구독의 재조회를 끝낸 뒤 등록을 재개하면, V=10 메시지가 그 구독에 가지 않고 회수된다(판단은 구독이 아니라 방 참여 캐시로 한다, 다시 읽기는 방 단위 직렬화, 낮은 버전으로 덮지 않음). 늦은 회수 신호도 결정적으로 재현한다: 세대 1 퇴장 커밋 → 재입장해 세대 2로 새 구독 → 세대 1의 즉시 회수가 뒤늦게 실행되면 세대 2 구독은 남는다(퇴장 결과의 끝난 세대 이하만 회수). 캐시가 재입장 전에 읽힌 채 재입장 전 메시지가 늦게 오면 회수 전에 다시 읽어 새 세대 구독을 지우지 않는다. 늦은 `RECHECK_USER`는 자격이 돌아왔으면 닫지 않는다. 구독 허가(비참여·옛 세대·종료 방·자격 상실·구독 수 상한)의 거절과 연결 유지, 경로 규칙(다른 회원 큐·`/queue`·그 밖의 `/topic` 구독과 `/topic` SEND의 ERROR 종료, 브로커가 `/topic` 구독을 등록하지 않음), 구독 순간 전후 메시지 유실은 허용 범위이며(Q23) 주기 대조로 수렴하는지, UNSUBSCRIBE·DISCONNECT·연결 종료 때 구독 정리를 검증한다.
- 방별 Redis 채널(2026-10-30 사용자 결정): 첫 로컬 구독자에서 방 채널 SUBSCRIBE, 마지막 구독자 뒤 유예 후 UNSUBSCRIBE, 같은 방 동시 SUBSCRIBE의 한 번 추가, 해제 직후·해제 중 재구독, 재연결 중 추가·제거가 재연결 뒤 컨테이너 채널 목록과 맞는지 검증한다. 앱 방 채널 수 상한의 `SERVER_BUSY` 거절, 재연결 뒤 서버 채널만으로 재구독을 감지해 `RESYNC`를 보내는지(방 채널의 재추가는 재구독으로 보지 않음) 확인한다. 방 채널 구독자 0명을 발행 성공으로, 서버 채널 구독자 0명을 자기 구독 단절(멈춤·재확인)로 다루는지 시험한다. 구독 순간(방 채널 구독 확인 전) 발행된 메시지를 놓치는 것은 허용 범위다(Q23).
- Redis 접속 정보(Q21): 연결·끊김·하트비트로 `presence:online`·회원 연결 ZSET이 맞는지, 마지막 연결이 끊기면 `online`에서 빠지는지(다른 연결이 남으면 남는지), 하트비트가 멈춘 연결(비정상 종료·재시작)이 만료로 정리되는지, 알림 대상이 방 참여자 ∩ 접속 회원 − 방 구독 세션인지, 퇴장한 회원이 마지막 메시지 버전 규칙으로 빠지는지, 1000명 방에서 묶음마다 DB 조회 없이 `ZMSCORE` 1회인지 확인한다.
- 실시간 경로 경합 회귀(구현 리뷰, 2026-10-30):
  - Redis 구독 확인이 늦어도 방 채널 잠금이 기다리지 않아 다른 방의 구독·해제·연결 종료가 막히지 않고, 해제 직후 재구독은 마지막 상태로 컨테이너에 맞는다.
  - 방 채널 추가·제거가 실패하거나 시간을 넘기면 구독을 재설정해 실제 Redis 구독(`PUBSUB NUMSUB`)과 드라이버가 기억하는 채널이 원하는 방과 같아지고(거듭 실패해도 늘지 않음), 늦게 끝난 명령이 상태를 흔들지 않으며, 재설정이 `REALTIME_RESUBSCRIBED` 재구독 신호를 내고, 주기 정리는 실패해도 멈추지 않는다.
  - Redis가 느릴 때 해제 대기 방이 상한을 차지하고(구독·해제 반복이 쌓이지 않음), 앱 종료 때 방 채널 구독이 컨테이너보다 먼저 멈추고 실행기 스레드가 끝난다.
  - 새 메시지 알림 기록이 방 묶음을 얻은 직후 묶음 주기가 그 묶음을 떼어 가도 그 메시지를 잃지 않는다.
  - 살아 있는 연결이 회원 연결 키의 만료를 늘려도, 만료된 회원 연결 원소(재시작 전 앱·끊김 기록 실패)는 연결·하트비트 때 지워진다.
  - 알려진 한계(시험 대상 아님, 설계 4.2 "알려진 한계"): 늦게 재개된 해제가 같은 방의 새 구독을 지우는 경우와, 드라이버 호출이 구독 잠금을 잡은 채 멈춰 방 채널 I/O가 재시작 전까지 멈추는 경우. 두 경우에도 퇴장 뒤 미전달과 메시지 보존(이력 조회)이 지켜지는지만 확인한다.
  - 전송 ID 없이 보낸 일반 메시지도 보낸 사람 회원 큐로 전송 결과 확인(`clientMessageId: null`)을 받고, 시스템 안내·알림은 받지 않는다.
- 방 topic 비용: 참여가 고정된 1000명 방에서 메시지마다 DB 조회가 없고, 참여 변경 뒤 첫 메시지에서만 배치 재조회가 한 번 일어나는지 센다. 본문 프레임은 방을 구독한 세션 수만큼, 새 메시지 알림은 구독하지 않은 세션 수 ÷ 묶음 주기만큼인지 측정하고, 알림 대상이 묶음 마지막 버전 이상을 반영한 방 참여 캐시 ∩ 로컬 연결 회원 ∩ Redis 접속 회원 − 구독 세션인지(퇴장자 제외, 집합 항목은 읽지 않음), 방 참여 캐시를 새 버전마다 한 번만 다시 읽는지와 캐시 메모리 상한을 확인하고, Pub/Sub payload에 수신자 목록이 없는지 확인한다. 송신 대기열 상한·세션 송신 버퍼 초과 시 연결 종료와 재동기화를 확인한다.
- chat-app은 replica 1개로 검증한다. k3d E2E에서도 앱 1개에 여러 사용자·동일 회원의 여러 세션을 연결해 전달·연결 종료·재연결 이력 복구를 확인한다. 복수 replica E2E를 완료 조건으로 요구하지 않는다.

## 출시 전 급증·잠금 검증

초기 사용자 수를 근거로 생략하지 않는다. 상세 모델·수용 기준은 [설계 문서](../final-design.md) 4.6·4.7과 Q12를 따른다.

- **잠금 구간**: 전체 참여자 엔티티 조회·수신자 배열 생성·JSON·외부 I/O가 저장 트랜잭션에 남지 않는지 검증한다. 잠금 획득 대기와 획득 후 commit/rollback까지 유지 시간을 나눠 계측하고 변경 전후 동일 조건에서 비교한다. 메서드 반환만으로 잠금 해제를 판단하지 않는다.
- **수신자 집합**: 참여 행·집계·불변 집합 버전·포인터 갱신의 원자성, 메시지의 버전 참조, 퇴장·재입장 안내의 정확한 대상, 재처리·캐시 유실·집합 누락을 검증한다. 현재 목록으로 대체하지 않고, 미완료 작업의 참조 원본을 보존한다.
- **인기 방 폭주**: 1000명 접속과 같은 방의 초당 전송량·동시 입퇴장·읽음·이력 조회·기기 수를 분리해 증가시킨다. 여러 방의 같은 총량 시험과 비교하고, 느린 수신자·재접속 폭주·큰 메시지도 포함한다.
- **과부하 제어**: 입력·동시 실행·대기열·시간 초과·송신 버퍼 상한과 거절 응답을 확인한다. DB 진입 전 제한하고, 한 방의 폭주 중 다른 방·회원 제어·relay·Stream 소비/회수·복구가 진행되는지 확인한다. heap/RSS·스레드·DB 연결·큐 바이트가 지속 증가하지 않아야 한다.
- **장애·수용량**: Redis 중단·DB 지연·프로세스 종료 후 미완료 작업과 결과 미확인을 복구하고 동일 전송 ID의 재시도가 중복 저장으로 이어지지 않는지 확인한다. 성공 응답한 메시지 누락·참여 세대 유출은 허용하지 않는다. Q12의 수용 한도·p95/p99·허용 거절률·복구 목표와 설정값을 출시 전에 확정하고 결과를 남긴다.
