# 알림 대표 기준선 B0

알림(auxiliary-app notification) Kafka 소비 경로의 리팩토링 전 대표 기준선이다(N13, #946). N14 리팩토링 뒤 같은 조건으로 다시 재어 기능 동일성과 처리량 회귀를 판정한다. 정책·절차의 원본은 [알림 결정 기록](../notification/decisions.md) ND-155·ND-156·ND-163~ND-178이고, 이 문서는 수치와 회차의 원본이다.

## 측정 중 수집 장치(N14도 같게)

측정 구간에는 두 수집 장치가 함께 돈다. 둘 다 B0와 N14에서 같은 설정·절차로 유지한다(ND-176). 설정을 바꿔야 하면 B0와 N14의 측정 조건이 달라진다는 점을 먼저 보고하고 승인을 받는다.

| 장치 | 목적 | 실행 위치·방식 | 주기 | 받는 양 |
| --- | --- | --- | --- | --- |
| 완료 감지 polling | 정상 단계 완료 시각(처리량의 분모) | 도구 pod 안 `poll_latency_count.sh`가 앱 pod IP:8082에 `wget`, 이름 필터 `includedNames=hapbang_notification_consume_latency_seconds` | 0.5초(실제 평균 약 0.53초) | 약 7KB |
| 자원 sampler | Hikari 활성·대기, 앱 CPU·메모리 기록(ND-157) | 호스트(Git Bash)의 `b0.sh` `sampler()`가 port-forward로 전체 `/actuator/prometheus`를 `curl`, 이어서 `kubectl top pod`(앱) | 5초 | 지표 전체 약 634KB(약 1,650 series) |

- 자원 sampler는 지표 이름 필터를 쓰지 않는다. 앱이 5초마다 전체 지표를 만들어 응답한다.
- **한계**: 자원 sampler가 처리량에 주는 영향은 따로 정량 검증하지 않았다. 5초 간격이라는 이유만으로 영향이 없다고 보지 않는다. B0와 N14가 같은 조건이라 두 측정의 비교에는 같은 영향이 들어간다.
- 진단 수집(1초 앱 지표·VM CPU·PostgreSQL 활동, 스레드 덤프 3회)은 `B0_DIAG=1`일 때만 켜고 공식 회차에서는 끈다(ND-170).

## 측정 방법

- **정상 단계 처리량** = 4,925 ÷ 소요 시간. 소요 시간은 투입 시작(producer 실행 안 도구 pod 시계)부터, 알림 토픽 5개의 성공 처리 건수(`consume.latency` count)가 4,925만큼 처음 는 관측 시각(도구 pod가 0.5초마다 이름 필터 지표를 읽음)까지다. 같은 도구 pod 시계끼리만 뺀다(ND-167~ND-169).
- **관측 오차**: 완료는 도달 직전 관측과 도달 관측 사이 어딘가라 소요 시간이 최대 polling 간격만큼 짧았을 수 있다. 5회의 실제 최대 간격은 0.556~0.582초, 처리량 상대 오차는 2.6~2.9%다.
- **p95·p99**: 정상 단계 스냅샷(①~②)의 `consume.latency` histogram을 Prometheus `histogram_quantile`과 같은 구간 내 선형 보간으로 낸 추정치다. 레코드 timestamp부터라 Kafka 대기 시간을 포함한다. 투입(초당 약 300건)이 소비(초당 약 240건)보다 빨라 지연 대부분이 대기열 해소 시간이고, 10~30초 구간 폭 때문에 p95 +15%는 믿을 만하게 판정할 수 없다. 그래서 보조 지표로만 쓴다(ND-168).
- **실패 단계**: 복구 시간 = 실패 단계 투입 시작부터 DLT 75건·lag 0·지표 30초 안정까지(완료 감지 루프의 간격만큼 크게 잡힌다). 실패 레코드는 성공한 시도가 없어 지연 표본이 없다.

## N14 판정

ND-175를 따른다. N14 리팩토링 뒤 같은 fixture(`bea6c107…`)·B0 설정·`b0.sh` 절차로 5회를 잰다.

1. 5회 모두 V0~V8 통과, F가 B0와 같다(`5a7ab852…`).
2. 처리량 CV ≤ 10%. 넘으면 다시 잰다.
3. 처리량 중앙값 ≥ 213.8건/초(B0 중앙값 237.52의 90%).
4. p95·p99가 다른 구간으로 옮겨 가거나 비정상적으로 나빠지면 처리량이 합격이어도 원인을 분석해 보고한다.

## 한계

- 노트북 k3d 수치라 운영 처리량·지연을 뜻하지 않는다. 운영 확인은 N15·N16이다.
- `synchronous_commit=off`라 커밋이 디스크 동기화를 기다리지 않는다. 운영(기본값 on)에서는 레코드마다 커밋하는 비용이 더 크다.
- p95·p99는 histogram 보간 추정치다(위 측정 방법).
- 투입이 소비보다 빨라 처리량은 "대기열이 쌓인 상태의 소비 속도"다. 레코드별 처리 지연은 투입 속도를 통제하는 N15에서 잰다.
- 운영 smoke(L1·L2)는 이 문서 작성 시점에 실행하지 않았다(미실행, 알림 담당이 실행).

느린 회차는 커밋의 WAL 디스크 동기화 대기가 처리량을 약 1/10로 떨어뜨렸다. 행 잠금 대기, CPU(VM 최대 66~70%, throttling 불가), Hikari 대기, 스레드 차단, 검색 모듈 ES 재시도(투입 전부터 약 2초 간격)와는 상관이 없었다. 알림 저장이 레코드마다 커밋하므로 Docker Desktop VM 디스크의 fsync 변동이 그대로 처리량 변동이 됐다. 그래서 B0 database만 `synchronous_commit=off`로 두고 공식 5회를 다시 쟀다(ND-170).

## 운영 smoke 실행 방법(L1·L2)

운영 쓰기가 없는 확인만 한다(ND-171). 계정 준비·공지·실행은 알림 담당이 한다(ND-174). k6는 버전을 고정한 컨테이너로 돌린다.

1. 계정 파일 `~/.hapbang/load-tests/notification.env`(권한 0600, 레포 밖)에 `LT_EMAIL`, `LT_PASSWORD`, `WS_ORIGIN`(운영 FE 주소)을 둔다.
2. 레포 루트에서 Git Bash로 실행한다. 비밀 값은 명령줄에 쓰지 않고 환경 변수 이름만 넘긴다.

```bash
set -a; . ~/.hapbang/load-tests/notification.env; set +a
export MSYS_NO_PATHCONV=1
OUT="$HOME/.hapbang/load-tests/runs"
docker run --rm -v "$(pwd -W)/loadtest/k6:/scripts:ro" -v "$(cd "$OUT" && pwd -W):/out" \
  -e BASE_URL -e LT_EMAIL -e LT_PASSWORD -e PROFILE=smoke \
  grafana/k6:1.0.0 run --summary-export /out/k6-notification-rest-smoke.json /scripts/notification/rest.js
docker run --rm -v "$(pwd -W)/loadtest/k6:/scripts:ro" -v "$(cd "$OUT" && pwd -W):/out" \
  -e BASE_URL -e LT_EMAIL -e LT_PASSWORD -e WS_ORIGIN -e PROFILE=smoke \
  grafana/k6:1.0.0 run --summary-export /out/k6-notification-stomp-smoke.json /scripts/notification/stomp.js
```

3. 커밋할 요약은 허용 목록·민감 패턴 검사를 거친다. 검사에 걸리면 저장하지 않는다.

```bash
python -I loadtest/k6/notification/sanitize_summary.py "$OUT/k6-notification-rest-smoke.json" docs/load-test/results/notification-rest-smoke.json
python -I loadtest/k6/notification/sanitize_summary.py "$OUT/k6-notification-stomp-smoke.json" docs/load-test/results/notification-stomp-smoke.json
```
