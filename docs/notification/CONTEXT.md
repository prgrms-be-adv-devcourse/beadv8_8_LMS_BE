## 1. 알림센터 도메인의 책임

알림센터는 다른 모듈에서 일어난 사건을 받아, 그 사건을 알아야 할 회원에게 **앱 안에서** 안내 한 건씩을 만들어 보관하고 보여 주는 도메인이다.

| 맡는 것 | 관련 ND |
| --- | --- |
| 종 아이콘으로 여는 알림 목록, 안 읽은 수 배지, 읽음 처리 | ND-001 |
| 다른 모듈의 사건(Kafka integration event)을 받아 받는 사람·종류·문구를 정하는 일 | ND-008 |
| 알림 저장·보존·조회, 실시간 전달 | ND-019~027 |
| 정한 시각에 보내는 예약 알림, 하루 묶음 알림 | ND-029~032 |

| 맡지 않는 것 | 관련 ND |
| --- | --- |
| 이메일·푸시, 로그인하지 못한 회원에게 가야 하는 알림 | ND-002 |
| 관리자에게 가는 업무 알림(관리자 화면 목록이 맡는다) | ND-003 |
| 채팅의 알림(출연 알림 메시지, 단체방 안내, 실시간 새 메시지 알림), 채팅 새 메시지·차단 | ND-004, 5장 |
| 발행 모듈의 상태 변화 자체(알림센터는 사건을 받기만 한다) | ND-008 |

## 2. 개념

### 2.1 알림과 알림센터

- **알림**: 서비스가 회원에게 상태 변화를 알리는 안내 한 건(GLOSSARY). 운영자 장애 통보(alert)와 다르다.
- **알림센터**: 알림을 모아 보여 주는 화면 기능과 그것을 맡는 모듈(auxiliary-app의 `notification` 모듈, ND-006). 알림은 "한 건", 알림센터는 "그 건들을 다루는 곳"이다.
- 채팅 안에도 "알림"이라는 말이 붙은 개념이 있다. 이름이 같아도 알림센터의 알림이 아니다(5장).

### 2.2 알림 종류와 종류 코드

- **알림 종류**: 알림이 어떤 사건을 알리는지 나누는 단위(예: 출연 요청 도착, 충전 완료). 즉시 알림 48종과 예약 알림 5종이 있다(ND-011, 고객센터 답변 수정을 뺀 수는 ND-123). 종류별 받는 사람·발생 조건·보내지 않는 것은 [알림 종류](notification-catalog.md)에 있다.
- **종류 코드**: 알림 종류를 코드로 쓴 이름. 원본 이벤트 이름에서 만든다(ND-012). 채팅과 같은 이름(`GROUP_*`)은 그대로 쓴다(ND-043). 규칙 밖의 코드 중 승급 승인은 ND-071, 하루 묶음은 ND-098, 예약 5종은 ND-137이다.
- 하나의 원본 이벤트가 여러 종류로 나뉠 수 있다(예: 지급 완료 이벤트가 출연 지급 한 건씩과 강의 지급 하루 묶음으로 나뉜다, ND-013).

### 2.3 즉시 알림과 예약 알림

| 개념 | 뜻 | 관련 |
| --- | --- | --- |
| 즉시 알림 | 원본 이벤트를 받으면 바로 만드는 알림 | ND-011 |
| 예약 알림 | 원본 이벤트로 "보낼 시각"을 정해 두고, 그 시각이 되면 만드는 알림. 취소 이벤트가 오면 보내지 않는다 | ND-029~031, ND-133, ND-134(운영 시간, 팀 확인은 U6) |
| 예약 | 예약 알림을 보내기 전까지의 기록(`notification_schedule`). 예약·보냄·취소·건너뜀 상태를 가진다. 끝난 기록은 업무 기한이 지나고 일정 기간 뒤 지운다 | ND-025, ND-135, ND-136, ND-142 |
| 업무 기한 | 예약 알림이 알리는 기한(수락 기한, 모집 마감, 방송 예정, 자동 확인, 자동 구매 확정). 이 시각이 지나면 그 예약 알림을 보내지 않는다 | ND-135, ND-143 |

### 2.4 하루 묶음 알림

여러 사건을 알림 한 건으로 합친 알림이다. 지금은 강의 지급 하나뿐이고, 판매자·날짜마다 한 건이다. 사건이 더 올 때마다 같은 알림이 갱신된다(ND-032). **묶음 키**(묶음 알림의 날짜)로 같은 묶음을 찾는다(ND-019, ND-025). 보존 20개에서 밀려난 묶음에 같은 날 새 사건이 오면 묶음이 되살아난다(ND-097).

### 2.5 받는 사람

알림을 받는 회원 한 명. 유저·인플루언서·인증된 인플루언서이고 관리자는 아니다(ND-003). 이벤트 하나가 여러 받는 사람에게 각각 알림을 만들 수 있다(예: 이의 제기 접수는 구매자·판매자, ND-015). 탈퇴한 회원에게는 만들지 않는다(ND-018). 정지 회원에게도 만들지 않는다(ND-072).

### 2.6 원본 이벤트 종류와 원본 대상 ID

- **원본 이벤트 종류**: 알림을 만든 integration event의 종류.
- **원본 대상 ID**: 그 사건을 한 번만 나타내는 ID(ND-033). 같은 대상에서 여러 번 날 수 있는 사건이면 업무 대상의 ID와 다르다. 발행 모듈에 회차 ID가 없으면 `<대상 ID>:<회차>`다(ND-045).
- 두 값과 받는 사람이 같은 알림은 한 번만 만든다(ND-019). 종류별 필드는 [알림 종류](notification-catalog.md) 각 행에 있다(N5 11종은 ND-073). 그 밖의 이미 발행 중인 이벤트는 **미결**이다(U5).
- 원본 대상 ID는 다른 모듈의 ID를 값으로만 갖는다. 다른 모듈 테이블과 FK·JOIN하지 않는다(루트 AGENTS 3장, ND-007).

### 2.7 이동 대상

알림을 눌렀을 때 화면이 이동할 대상(종류·ID). 화면이 아니라 업무 자원 단위다(ND-074). 원본 대상과 같을 수도 다를 수도 있다(ND-025). 대상이 삭제됐어도 알림은 남고, 이동한 화면이 삭제됐다고 보여 준다(ND-024).

### 2.8 발생 시각 (업무 시각)

알림이 알리는 사건이 업무상 일어난 시각. 알림센터가 이벤트를 **받은 시각**이나 행을 **만든 시각**과 다르다. 목록 순서와 보존은 발생 시각으로 정한다(ND-021, ND-022). 이벤트에 사건 시각이 없으면 Kafka 레코드 timestamp(발행 시각)를 대체 시각으로 쓰고, 이 값은 실제 사건 시각과 같다고 보장하지 않는다(ND-081). 하루 묶음 알림은 갱신될 때 발생 시각이 새로 바뀐다(ND-032).

### 2.9 문구와 값

- **문구**: 회원에게 보이는 안내 문장. 알림 모듈이 만들어 저장한다(ND-020). 종류별 문구는 그 종류를 소비하는 작업에서 정한다(ND-039·ND-050). N5 11종은 [알림 종류](notification-catalog.md) 0.5(ND-075)이고 나머지는 미결이다(U3). 지급 알림은 지갑이 제목을 발행하기 전에는 제목 없이 만든다(ND-070).
- **값**: 문구를 다시 만들 수 있게 함께 저장하는 사실(ID, 제목, 금액, 일시 등, ND-008·ND-020). 지급 알림의 제목은 지급 이벤트의 출처 제목으로 받는다(ND-040).

### 2.10 생성·저장·조회

| 단계 | 뜻 | 관련 |
| --- | --- | --- |
| 생성 | 이벤트를 받아 받는 사람·종류·문구·값을 정하는 일. 같은 이벤트를 다시 받아도 한 번만 생긴다 | ND-008, ND-018, ND-019 |
| 저장 | 알림을 회원별 최신 20개로 보관하는 일. 밀려난 알림은 Soft Delete되고 되살아나지 않는다 | ND-022, ND-025 |
| 조회 | 로그인 회원이 자기 알림만 보는 일(목록, 안 읽은 수) | ND-026 |
| 실시간 전달 | 저장된 알림을 연결된 화면에 바로 보내는 일. 유실될 수 있고 DB가 원천이다 | ND-027 |

### 2.11 읽음과 안 읽은 수

- **읽음**: 회원이 알림을 눌렀을 때 그 알림이 읽은 상태가 되는 것. 목록을 연 것만으로는 읽지 않는다. 전체 읽음도 있다(ND-023).
- **안 읽은 수**: 보존된 알림 중 읽지 않은 알림의 수. 배지에 쓰고 최대 20이다(ND-022). 하루 묶음 알림은 갱신되면 다시 안 읽음이 된다(ND-032).
- 채팅의 "안 읽은 메시지 수"와 다른 개념이다(5장).

### 2.12 알림 회원 (`notification_user`)

알림 모듈이 회원 이벤트로 만들어 갱신하는 회원 정보 복제본(상태·역할·닉네임). 가입 이벤트로 만들고, 복제본이 없을 때 온 변경 이벤트로도 만든다(ND-049). 받는 사람이 탈퇴했는지 확인하고, 역할 변화로 승급 승인 알림을 알아내는 데 쓴다(ND-016, ND-018). 채널 인증 승인은 회원의 승인 이벤트로 받는다(ND-042). 채팅의 `chat_user`와 같은 방식이었으나 변경 이벤트로 만드는 점이 다르다. 회원 모듈의 테이블을 직접 읽지 않는다(루트 AGENTS 3장).

### 2.13 연결 티켓

알림 실시간 연결(WebSocket)을 열기 전에 REST로 받아, 연결할 때 내는 티켓. 채팅 연결 티켓(`/api/v1/chats/ws-tickets`)과 같은 방식이지만 알림 모듈 자체의 것이다(ND-027, ND-028). 유효 시간·발급 제한은 ND-058, 연결 만료는 ND-056이다. 경로는 [API 문서](../api/notification.md)에 있다.

## 4. 개념 관계도

```text
발행 모듈 (출연·강의·지갑·회원·고객센터·채팅)
  └─ integration event (사실만: ID·제목·금액·일시)              ND-008
       │  원본 이벤트 종류 + 원본 대상 ID (ND-033·ND-045, N5는 ND-073, 그 밖은 U5)
       ▼
알림센터 (auxiliary-app notification 모듈)
  ├─ 알림 회원 (notification_user) ── 받는 사람 확인 · 역할 변화   ND-016, ND-018
  ├─ 알림 종류 / 종류 코드                                       ND-011, ND-012
  │
  ├─ 즉시 알림 ─────────────┐
  ├─ 예약 ─(보낼 시각)─▶ 예약 알림 ─┤                             ND-029
  └─ 하루 묶음 (묶음 키) ───────┤                                 ND-032
                             ▼
```

## 5. 채팅 개념과의 구분

채팅에도 "알림"이 붙은 개념이 있다. 아래 채팅 개념은 채팅이 소유하며 알림센터가 계약을 정하지 않는다(ND-004, decisions.md 12장). 채팅 계약 원본은 [`apps/chat-app/docs/contracts/notification-data.md`](../../apps/chat-app/docs/contracts/notification-data.md)다.

| 채팅 개념 (채팅 소유) | 무엇인가 | 알림센터와의 관계 |
| --- | --- | --- |
| 출연 알림 메시지 | 출연 이벤트로 1:1 채팅방에 남기는 메시지(GLOSSARY) | 같은 출연 이벤트를 알림센터도 따로 받아 알림을 만든다. 둘 다 남는다(ND-004). 화면에서 어떻게 보일지는 U12 |
| 단체방 안내(`SYSTEM` 메시지) | 단체방 초대·강퇴·폐쇄를 방 안에 남기는 안내 | 알림센터는 방을 열지 않은 회원에게 따로 알린다(ND-011). 채팅 안내는 그대로다 |
| 채팅 `NOTIFICATION` 메시지와 `NotificationKind` | 채팅 메시지의 한 종류와 그 종류 이름 | 알림센터 종류 코드와 만드는 규칙만 같다(ND-012). 별개 목록이다 |
| 실시간 새 메시지 알림 | 새 메시지 도착을 WebSocket(`/user/queue/chats/notifications`)으로 보내는 알림(GLOSSARY) | 알림센터에 넣지 않는다. 채팅 새 메시지·차단은 채팅의 안 읽은 메시지 수가 맡는다(ND-004) |
| 채팅 안 읽은 메시지 수 | 채팅방의 읽지 않은 메시지 수 | 알림센터의 안 읽은 수와 다른 값이다 |

**같은 `GROUP_*` 이름 주의**: 알림센터의 `GROUP_MEMBERS_INVITED`·`GROUP_MEMBER_KICKED`·`GROUP_ROOM_CLOSED`는 채팅 `NotificationKind`와 이름이 같지만 뜻과 받는 사람이 다르다(예: 강퇴는 채팅은 남은 참여자, 알림센터는 강퇴된 회원). 이름은 그대로 쓰고 이 차이를 문서에 적는다(ND-043). 코드나 문서에서 이 이름을 볼 때 어느 쪽 개념인지 먼저 확인한다.
