# 도메인 문서

엔지니어링 스킬이 코드를 살펴볼 때 이 레포의 도메인 문서를 어떻게 읽는지 정한다. 레이아웃은 single-context다(멀티모듈이지만 용어집과 결정 기록은 레포 하나에 둔다).

## 살펴보기 전에 읽을 것

- **`docs/GLOSSARY.md`**: 이 레포의 유비쿼터스 언어(용어집)다.
- **`docs/policy.md`**: 돈·HP 규칙과 역할·권한 표다. 모듈별 정책은 아래 모듈 문서의 "정책 요약" 장에 있다. 원본은 레포 밖 기획서("결제·HP·정산 정책" 표 등)이고, 레포 문서는 그 요약이다. 레포 문서에 없는 정책 수치는 지어내지 않고 묻는다.
- **모듈 문서**: 모듈의 정책·설계·결정 기록(D번호, 예: D46)이다. 작업할 모듈의 문서를 읽는다.
  - 강의: `docs/lecture/module.md`(2장 정책 요약, P번호)
  - 출연: `docs/appearance/module.md`(2장 정책 요약)
- **`docs/adr/`**: 있으면 작업할 영역에 닿는 ADR을 읽는다.

`docs/adr/`가 없으면 **조용히 넘어간다**. 없다고 지적하거나 미리 만들자고 제안하지 않는다. `/domain-modeling` 스킬(`/grill-with-docs`, `/improve-codebase-architecture`에서 이어짐)이 용어나 결정이 실제로 정해질 때 만든다.

**용어집 경로는 `docs/GLOSSARY.md`다.** 스킬 문서가 "루트의 `GLOSSARY.md`"라고 해도 이 경로로 읽고 쓴다. 레포 루트에는 `GLOSSARY.md`를 만들지 않는다.

## 파일 구조

```
/
├── AGENTS.md            ← 3장 모듈 경계, 4~6장은 아래 두 파일 링크
├── docs/
│   ├── GLOSSARY.md      ← 용어
│   ├── policy.md        ← 돈·HP 규칙, 역할과 권한
│   ├── lecture/         ← 강의 모듈 정책·설계·결정 기록(P·D번호)
│   ├── appearance/      ← 출연 모듈 정책·구조
│   └── adr/             ← (생기면)
└── boundedContext/<모듈>/
```

## 용어집의 말을 쓴다

결과물(이슈 제목, 리팩터링 제안, 가설, 테스트 이름)에서 도메인 개념을 말할 때는 `docs/GLOSSARY.md`의 용어를 쓴다. 비슷한 다른 말로 바꾸지 않는다. 예: "구매 취소"와 "환불", "지급"과 "정산"은 서로 다른 말이다.

필요한 개념이 용어집에 없다면 신호다. 프로젝트가 쓰지 않는 말을 지어내고 있거나(다시 생각한다), 실제로 빠진 용어다(`/domain-modeling`에 넘길 거리로 적는다).

## 결정과 충돌하면 드러낸다

결과물이 기존 정책(`docs/policy.md`, P번호)이나 결정(D번호, ADR)과 어긋나면 조용히 덮어쓰지 말고 밝힌다.

> _D46(주문 행 잠금)과 어긋나지만, …때문에 다시 볼 만하다._
