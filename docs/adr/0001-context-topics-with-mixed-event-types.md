# 발행 컨텍스트마다 토픽 하나에 이벤트 타입을 섞는다

Kafka 토픽은 이벤트 타입이 아니라 발행 컨텍스트 단위로 하나씩 둔다(`member.events.v1`, `appearance.events.v1`). 같은 대상의 이벤트(회원 가입 → 변경, 출연 취소 요청 → 수락)가 같은 key로 같은 partition에 들어가야 순서가 지켜지기 때문이다. 타입별 토픽은 소비자가 필요한 타입만 구독할 수 있지만 이 순서를 잃는다. 결정 과정은 #339다.

## Consequences

- 소비자는 토픽의 모든 타입을 받는다. 클래스 레벨 `@KafkaListener`에 받을 타입마다 `@KafkaHandler`를 두고, 모르는 타입은 `@KafkaHandler(isDefault = true)`에서 무시하고 커밋한다. 메서드 하나가 특정 타입만 받으면 다른 타입이 변환 오류로 DLT에 쌓인다.
- 새 이벤트 타입을 추가할 때는 소비 앱을 먼저 배포하고 발행 앱을 나중에 배포한다. 소비 앱에 클래스가 없으면 역직렬화부터 실패한다.
- 깨지는 payload 변경도 같은 토픽에 새 레코드 타입으로 추가한다. 토픽의 `.v<N>`은 key·partition 계약이 바뀔 때만 올린다.
- 토픽에 compaction을 쓰지 않는다. compaction은 key마다 마지막 메시지만 남기므로 여러 사실이 섞인 토픽에서는 최신 상태를 보장하지 못한다.
- 토픽 이름에는 소비자 관점의 말(예: "notification")을 넣지 않는다. 발행자는 사실만 내고 해석은 소비자가 한다.
